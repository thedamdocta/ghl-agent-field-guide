# Pattern — Imposing a Design System on GHL

GHL will let you build a page that looks like a GHL page very easily, and will fight
you at four specific points if you want it to look like something else. This is what
those four points are, and how to hold a real design system across both funnel pages
and email — which are, mechanically, two completely different problems.

---

## 1. The constraint everything else follows from

**GHL does not compile an element's `styles` object into CSS at render time.**

The builder generates a CSS string *client-side* and stores it on each section at
`general.sectionStyles`, with every rule scoped to a specific element id:

```css
.hl_page-preview--content .section-<id>{box-shadow:none;padding:12px 5%}
@media screen and (min-width:0px) and (max-width:480px){
  .hl_page-preview--content .section-<id>{padding-top:10px!important} }
```

So `styles` is the builder's editing state and `sectionStyles` is what the browser
actually sees. A from-scratch generator that sets every style property, posts a valid
tree and gets a `201` renders as **completely unstyled overlapping text** — proven in
production on a seven-section page with all copy present.

Two routes out of this, and the choice determines what design you are allowed to have:

- **Reuse an existing page's ids.** Clone a page (or one generated by GHL's own AI),
  rewrite the text nodes, **preserve every element id** so the stored `sectionStyles`
  still matches. Cheap and reliable. You inherit that page's layout and cannot express
  an arbitrary design.
- **Emit `sectionStyles` yourself for your own ids.** The mapping is mechanical.
  This is the only route that injects an arbitrary design as native, editable GHL
  elements. `tools/css_emitter.py` in this repo does it.

---

## 2. Emit for BOTH id namespaces

Every node carries two ids and they are not interchangeable:

| id | what it governs |
|---|---|
| `node.id` | the **authoring** id. Section- and row-level layout keys off it. |
| `node.extra.nodeId` | the **rendered** id, conventionally `c`-prefixed. Element-level styling — button fills, heading typography, nav items — keys off **this** one. |

GHL's own builder emits rules for both. If you emit only the authoring id, your
sections lay out correctly and every button, heading and nav item renders in default
styling. The symptom reads as *"my CSS is being ignored"* when in fact half of it
landed on a selector that matches nothing on the page.

Emit a grouped selector covering both:

```
.hl_page-preview--content .<authoringId>,
.hl_page-preview--content .<renderedNodeId> { … }
```

One asymmetry, verified and deliberate: **`mobileStyles` is scoped to the authoring id
only** — that is what the builder emits and what was observed working. If a mobile
override is not landing on an inner element, that asymmetry is the first place to
look.

**Type lives on `extra`, not `styles`.** `extra.desktopFontSize`,
`extra.mobileFontSize` and `extra.typography` are where the builder keeps type. You
can set `fontSize` inside `styles` all day and see nothing change.

---

## 3. The injection-order problem

Three stylesheets end up on the page and you control the content of two of them and
the order of none:

1. GHL's own platform stylesheet,
2. the per-section `sectionStyles` strings, in section order,
3. whatever you put in the page-level custom-code block.

Consequences, each of which cost time:

**GHL's stylesheet outranks a plain rule of yours for a specific handful of
properties.** `background-color` is the loud one: without `!important` every section
renders transparent and the whole page flattens to a single ground colour. The emitter
force-flags a small set — background-color, color, padding-top, padding-bottom — and
you should add to it whenever a property of yours is visibly being overridden rather
than reaching for a heavier selector.

**Match the builder's own media query string verbatim** —
`@media screen and (min-width:0px) and (max-width:480px)` — rather than "improving" it
to a plain `max-width`. Identical query text is what keeps your rules and GHL's from
interleaving in a surprising order when both are present on the same page.

**Replace `sectionStyles` wholesale; never merge into it.** Your emitter is the source
of truth for styling. If you append, a stale hand-edit from the builder survives and
silently fights your generated rules, and the winner depends on emission order — which
is the single hardest class of bug to diagnose here because the page looks *almost*
right.

**The page-level custom-code block is a system stylesheet, not a patch.** Section
styles are per-element and per-section; the design system — the type scale, the
spacing scale, the button treatment, the component classes — belongs in one page-level
stylesheet applied through custom code. Because it sits at a different level from the
id-scoped rules, it needs `!important` on almost everything to impose itself. That
looks alarming and is correct here: you are deliberately overriding a generated
stylesheet you do not own. Write it once, ordered
`containment → layout → type → components → ornament → hero → motion`, and treat any
rule that has to be added later as evidence the system is incomplete rather than as a
patch.

**Custom-code block rules that are not documented anywhere:**

- `<script>` must **not** be nested inside a `<div>` — siblings only.
- Wait for GHL's `hydrationDone` before touching the DOM.
- In page settings, "Optimise JavaScript" must be **off** or hydration defers and your
  script runs against a tree that is not there yet.

**Fonts: `<link>` with `preconnect`, not `@import`.** `@import` serialises the font
fetch behind the stylesheet parse and delays first paint. On a type-led design that is
the whole first impression.

## 4. Use an established token set, defined once

Define the palette, the type stack and the spacing scale in **one module**, and let
every surface import from it: the page CSS emitter (as `:root` custom properties), the
page-level stylesheet, and the email builder.

Three things this build learned the hard way:

**Collapse near-duplicate registers.** The palette carried three near-blacks that were
indistinguishable at render and existed only because three different documents had
each named one. They were mapped to a single hex behind their original names, so
callers did not change and the design gained a real ground. If two tokens cannot be
told apart on screen, they are one token with two names, and the second name is a
future inconsistency.

**Key the spacing scale to viewport WIDTH only.** A section rhythm defined in `vh`
changes when browser chrome appears or disappears, which reads as the page breathing
for no reason. `clamp(min, Nvw, max)` throughout.

**Prefer an existing typographic system to an invented one.** This build used a
historically coherent old-style serif pairing with a real display/text distinction —
so the display face and the body face were designed together and the scale had
somewhere to go. Type scale on the pages ran roughly 100/46/29/21/16.5/11. Contrast
that with the reference we analysed, whose entire email scale was 13/14/16 — body and
headings effectively the same size, so every message read as one undifferentiated
block. Extreme scale contrast is the cheapest way to look designed, and it requires a
type system that supports it.

## 5. Email is a different platform

Everything above applies to funnel pages. Email shares the tokens and nothing else.

**Table-based layout with the `bgcolor` attribute as well as the inline style.**
Outlook on Windows renders through the Word engine and ignores CSS backgrounds on
divs, float and most positioning. Anything load-bearing is a `<table>`.

**Every text node carries an explicit colour.** A dark-ground email that inherits its
colour is one client-side inversion away from black-on-black. That bug shipped once on
the pages in this build; it does not get to ship twice.

**The email may legitimately be light-ground while the site is dark.** Inbox clients
render dark backgrounds unreliably and several invert them outright. Carrying the
brand through the accent colour and the typography, and letting the ground differ, is
a better decision than fighting for a dark inbox. That is a considered inconsistency,
not a defect.

**The webfont fallback is doing real work.** Webfonts do not load in Outlook and are
unreliable elsewhere. Choose a fallback in the same genre with similar colour on the
page, so the sequence still reads as the same design when the webfont never arrives.

### SVG cannot travel into email

Inline SVG is the right answer on the pages — an ornament or a monogram drawn as SVG
costs no request and scales without an asset. **It does not render in Gmail.** So any
signature device that has to appear in both places must be **rendered to raster and
hosted on the platform's own media CDN.**

Two non-obvious parts:

**Render it on an opaque ground, not transparent.** A transparent PNG in a client that
force-inverts becomes, for example, gilt-on-white instead of gilt-on-black, and a
carefully weighted ornament falls apart. Baking the intended ground into the file
makes the asset immune to the inversion.

**Host on the platform's media library, not a third-party CDN.** A third-party
generation URL vanishes when its owner deletes the generation, and the returned URL
from the platform upload is the same form the builder itself uses, so it is safe to
reference from page CSS as well.

The counterpart rule: **anything that can stay live text should stay live text.** A
masthead typeset as real HTML survives image-blocking (Outlook's default), reflows on
a phone, and swaps by editing a value rather than commissioning a new file. A raster
banner with the headline baked into it buys total art direction and costs all three.
Where this build landed: ornaments and marks as raster, all type as live text. That
choice was flagged rather than settled, because it changes what assets you commission.

**Type into the editor; do not paste styled HTML into it.** The sequence we analysed
declared a font on its container and then had every inline span override it back to
Arial, so the theme font never applied anywhere. The same markup carried
`color:rgb(0,0,0)` three times in a single style attribute. Both are artefacts of
pasting styled text into a rich-text editor. If you are generating markup, push it as
raw HTML through the API instead — templates stored with `editorType: "html"`
round-trip byte-identical.

## 6. The custom-value rule, stated as a design principle

> **A custom value earns its place only when the same string must appear on more than
> one surface. Otherwise it should be literal text the client can see and edit.**

This belongs in a design-systems document because it is a design decision, not a
plumbing one. A custom value is a **variable in your design system**. Variables are
worth their cost when they enforce consistency across surfaces; a variable with one
consumer is not a variable, it is an indirection.

Measured on this build: of 75 modularised slots across 6 pages and 9 emails, only 16
were multi-surface. The business name and the legal footer appeared on all 15
surfaces; the event date on 5. The other 59 existed on exactly one page — where the
merge tag bought nothing and cost the client the ability to read their own copy in
the builder.

The consequence in practice: **48 slots were converted back to literal text**,
including every button label, seeded from the values that were already live so no copy
had to be invented and nothing shipped blank.

And the reason to care beyond tidiness: **unknown merge tags resolve to empty string,
silently, on every surface.** Every variable you introduce is a live silent-failure
site. Fewer variables is not just simpler, it is a smaller attack surface for the
platform's worst behaviour.

Two qualifications:

- **Apply the rule per editing surface, not globally.** Page copy becomes literal
  because the page builder is WYSIWYG. Email copy stays a merge tag because a raw-HTML
  template would mean asking a non-technical owner to edit markup to change a
  sentence. See `client-config-app.md` §2.
- **Multi-surface identity values stay variables and stay out of the client's reach.**
  A legal disclaimer on fifteen surfaces should be one string, and should not be
  editable from a webinar form.

## 7. Order of operations

```
1. define tokens in one module
2. build the element tree (authoring ids without the c prefix,
   extra.nodeId set to the c-prefixed form)
3. emit sectionStyles for every section, BOTH namespaces, root vars at :root
4. attach the page-level system stylesheet as a custom-code block
5. inject → expect 201
6. verify on the rendered preview, at the real viewport, in both orientations
7. for email: build tables, inline everything, raster the SVG onto its ground,
   upload to the platform CDN, push as editorType html, send a real test
```

Step 6 is not optional and step 7's last clause is the one that gets skipped. A `200`
is not a result on this platform; see `methodology/verification.md`.

---

## 8. Untested / unresolved

- **The builder regenerates `sectionStyles` when a human edits the page.** What
  happens to hand-emitted rules after a client edits a page in the builder was never
  observed across a full cycle. Assume your emitted CSS is not durable against builder
  edits until you have watched one.
- The live-text vs raster masthead decision was flagged, not settled.
- Whether custom values resolve inside the email builder identically to funnel pages
  was never round-tripped. They should. Verify before a real send.
